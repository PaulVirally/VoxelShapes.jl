# Writing style for code comments, docstrings, and docs

Paul writes the prose in this repository. Comments, docstrings, README text
and docs pages should read like his writing, not like a chatbot's. Two
reference samples follow, then the habits to copy and the tells to avoid.

## Sample 1: expository prose (from Paul's thesis)

> For any realistic system size, the W operator is impractical to compute
> directly. For example, for a relatively small computational domain of
> 2λ×2λ×2λ that is discretized to a resolution of 1/32 λ (a realistic resolution
> for a 3D inverse design problem), the W operator is a matrix that takes 10 TB
> of memory to store. Storing the matrix alone is already challenging on modern
> supercomputers, so computing the inverse of the matrix directly is not
> realistic. As such, solving eq. (3.1.4) can only realistically be done via
> iterative methods.
>
> Such methods solve the problem Ax=b starting with an initial guess x0, and
> generate a sequence of vectors x1, x2, ..., such that x_n → x as n → ∞. These
> vectors are generated by a formula x_{n+1} = f(Ax_n) where f(v) is some vector
> valued function that depends on the particular algorithm used. Note, however,
> that the input to f is the matrix-vector product Ax_n, that is, the input is
> just a vector, not a matrix. This allows us to solve large linear systems of
> equations without ever even having access to the matrix A. All that is needed
> for iterative methods is some program that can compute v_n = Ax_n efficiently.
>
> An important aspect of iterative methods is their convergence. Given a
> tolerance ε to which we want to solve the system, we would like to know how
> many iterations are needed to reach the converged state ∥Ax_n − b∥ < ε. It
> turns out the number of iterations depends strongly on the condition number,
> κ(A), of the matrix. The exact relation between the condition number and the
> number of iterations needed depends on the iterative method used, but the
> larger the condition number, the harder the problem is to solve.
>
> Note that the dependence of the number of iterations on the condition number
> is a "worst case" analysis. It is possible for a system with a large condition
> number to converge quickly. Additionally, it is possible to come up with
> preconditioners that do not necessarily reduce the condition number of the
> problem, but rather split up the problem into independent sub problems that
> are easier to solve.

What to copy from it:
- Plain declarative sentences, mostly medium length, some long ones with a
  concrete example folded in ("for a relatively small computational domain of
  2λ×2λ×2λ ... the W operator takes 10 TB").
- Concrete numbers and worked examples instead of adjectives.
- "Note that", "It turns out", "As such", "For example" as transitions. First
  person plural ("we would like to know", "we have tried") is fine.
- Explains *why* something is done, then *how*, in that order.
- No bullet lists in running prose. No headers inside a paragraph-sized
  explanation. No bold for emphasis.
- Occasional parenthetical asides that carry real information.

## Sample 2: Paul's docstrings

```julia
"""
    _vkffterr2string(err::UInt64)

Converts a VkFFT error code to a string.

# Arguments
- `err::UInt64`: The error code

# Returns
- A string representation of the error code
"""

"""
    _new_config(fft_dim::Int64, buffer_dim::Int64, dims::AbstractArray{Int64}, omit_dims::AbstractArray{Int64}, num_batches::Int64, coalesced_memory::Int64, aim_threads::Int64, num_shared_banks::Int64, forward::Bool, double_precision::Bool, inplace::Bool)

Wrapper for the VkFFT C function new_config.
"""

"""
    VkFFTPlan{T}(app::Ptr{Cvoid}, config::Ptr{Cvoid}, direction::Int32, dims::NTuple{N, Int} where N, region, buffer_size::AbstractArray{Int}, type::DataType, is_inplace::Bool)

A struct that holds the plan for a VkFFT operation.

# Fields
- `app::Ptr{Cvoid}`: The equivalent of an FFTW plan but for VkFFT
- `config::Ptr{Cvoid}`: A struct that holds the VkFFFT configuration
- `direction::Int32`: -1 for forward, 1 for inverse
- `dims::NTuple{N, Int} where N`: The size of the input array
- `region`: The dimensions on which to perform the FFT
- `buffer_size::AbstractArray{Int}`: The size of the buffer VkFFT will use (in bytes)
- `is_inplace::Bool`: Whether the plan is in-place (for optimization)
"""

"""
    _make_plan(x::CuArray{T}, region, forward::Bool, inplace::Bool; coalesced_memory::Int=0, aim_threads::Int=0, num_shared_banks::Int=0)

Creates a VkFFT plan for the given input array.

# Arguments
- `x::CuArray{T}`: The input array
- `region`: The dimensions on which to perform the FFT
- `forward::Bool`: Whether to perform a forward FFT
- `inplace::Bool`: Whether to perform the FFT in-place
- `coalesced_memory::Int=0`: The number of coalesced memory banks to use (0 for automatic)
- `aim_threads::Int=0`: The number of threads to aim for (0 for automatic)
- `num_shared_banks::Int=0`: The number of shared memory banks to use (0 for automatic)

# Returns
- A VkFFTPlan
"""

"""
    _delete_plan(plan::VkFFTPlan)

Deletes a VkFFT plan.

Wrapper for the VkFFT C functions delete_app and delete_config.
"""
```

What to copy from them:
- Signature line, blank line, one sentence in the third person present
  ("Converts ...", "Creates ...", "A struct that holds ...").
- `# Arguments` / `# Fields` / `# Returns` sections with one short fragment per
  entry, no trailing period. Defaults are written into the argument name
  (`aim_threads::Int=0`) and explained in parentheses ("0 for automatic").
- Detail goes where the reader needs it (what a field means, what a flag does)
  and is omitted where it would repeat the signature. A thin wrapper gets one
  line ("Wrapper for the VkFFT C function new_config.") and nothing else.
- Not every function gets a docstring. Public API and structs do. Small private
  helpers usually get a one-line comment above them instead, or nothing.
- No `# Examples` unless the usage is not obvious from the signature. No
  `# Throws` unless the error is part of the contract the caller relies on.
- No "This function ..." openers. No "Note that this is important" filler.

## Tells to remove (from the humanizer skill)

Read `/Users/pvirally/.claude/skills/humanizer/SKILL.md` for the full list.
The ones that show up most in generated Julia code and docs:
- Em dashes and en dashes. Paul's sample has none. Use a period, comma, colon
  or parentheses instead.
- "-ing" tails that add fake depth ("..., ensuring correctness", "...,
  allowing the kernel to ..."). Say the fact in its own sentence or cut it.
- Rule of three lists forced into a sentence.
- AI vocabulary: crucial, key (adjective), robust, seamless, leverage,
  comprehensive, ensure (as a filler verb), enhance, facilitate, streamline,
  showcase, highlight, underscore, delve, pivotal, elegant.
- Bold in running prose. Inline-header bullet lists ("- **Performance:** ...")
  in README and docs pages.
- Comments that narrate the diff ("Changed to use X instead of Y") rather than
  describe the code as it is.
- Comments that restate the line below them ("# increment i"). A comment
  earns its place when it says why, or states a non-obvious invariant.
- Copula avoidance ("serves as", "represents", "provides a way to"). Write
  "is", "has", "does".
- Hedging stacks ("may potentially", "in some cases can").
- Chatbot artifacts in docs ("Let's dive in", "Here's what you need to know",
  "Hope this helps").

When editing generated text, keep every fact and every code identifier. Do
not invent numbers or behavior that the code does not have. When unsure what
a sentence claims, read the code it documents.
